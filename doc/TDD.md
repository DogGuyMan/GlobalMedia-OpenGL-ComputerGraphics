# 테스트 계획 — 쉬운 설명판 (TDD 입문자용)

> **대상 독자**: "디버깅은 `printf`/로그 찍기랑 LLDB(디버거)로 멈춰보기밖에 모른다"는 사람.
> **목적**: 정식 설계( `doc/superpowers/specs/2026-06-27-test-expansion-design.md` )를 *쉬운 말 + 표준 용어*로 다시 풀어쓴 읽기용 보고서. 용어는 전부 업계 표준어(coin 아님 — 매핑은 spec §0.1).
> ※ 검증은 WebFetch 최소화 — 표준 정의는 교과서 출처(Feathers·Beck·Meszaros·Fowler) + 이미 외부 3-0 확인분만 인용.

---

## 0. 출발점: 네가 이미 아는 것 vs 테스트

| 네가 아는 방법 | 한계 | 테스트(자동화)가 주는 것 |
|---|---|---|
| **로그 (`printf`/spdlog)** | 매번 눈으로 출력을 *읽어야* 함. 코드 고치면 또 직접 확인 | 기대값을 **코드로 박아두면**, 빌드할 때마다 기계가 대신 읽고 PASS/FAIL |
| **LLDB(디버거)** | 한 번 멈춰서 *그 순간* 들여다봄. 다음에 또 깨지면 또 멈춰야 | 한 번 잡은 버그를 **회귀 테스트**로 박으면, 다시 깨지는 순간 자동 빨간불 |

**핵심 한 줄**: 테스트 = "로그로 눈 확인하던 걸, 기계가 매번 자동으로 해주는 것". LLDB로 한 번 본 걸 **두 번 다시 안 깨지게 못 박는 것**.

---

## 1. 꼭 아는 용어 (1줄 정의 + 네 경험에 빗대면)

- **단위 테스트(unit test)**: 함수 하나에 입력 넣고 결과가 기대대로인지 확인. → *로그로 "이 값 맞나?" 찍어보던 걸 코드로 고정.*
- **오라클(test oracle)**: "정답이 무엇인가"를 정해주는 기준. → *로그를 보고 네 머릿속에서 "이게 맞아"라고 판단하던 그 기준을, 코드/이미지로 외부화한 것.* (표준 SE 용어)
- **characterization test**(Feathers, *Working Effectively with Legacy Code*): "지금 돌아가는 동작"을 **있는 그대로 박아** 잠그는 테스트. 옳은지 따지지 않고 *현재 동작 = 정답*으로 고정 → 리팩토링하다 동작이 바뀌면 빨간불. → *"지금 잘 되니까, 이 상태를 스냅샷처럼 박아두자."*
- **회귀 테스트(regression test)**: 한 번 고친 버그가 **다시** 안 생기게 지키는 테스트. → *LLDB로 잡은 버그를 박아두는 그 테스트.*
- **fixture / mock / spy / SUT**(Meszaros, *xUnit Test Patterns*): 
  - **SUT** = 지금 시험 대상(System Under Test).
  - **fixture** = 테스트 돌리기 전 준비해두는 환경.
  - **mock/spy** = 진짜 의존 객체 대신 끼우는 *가짜* — spy 는 "무슨 호출이 왔나 기록"(나중에 내가 확인), mock 은 "잘못 부르면 스스로 실패".
  - → *로그를 박아둘 가짜 객체라고 생각하면 됨.*
- **red-green-refactor**(Kent Beck): 실패하는 테스트 먼저(red) → 통과시키고(green) → 정리(refactor). 단 우리는 대부분 **characterization**(이미 동작하는 걸 잠그는) 이라 red 부터 안 가도 됨.
- **golden image (= golden master = snapshot = approval test)**: "정답 스크린샷"을 한 번 찍어 저장 → 다음부터 새 출력과 **그림끼리 비교**. (네 용어 다 같은 뜻; 그래픽스에선 보통 *golden image*.) → *눈으로 "어 화면 똑같네" 확인하던 걸 픽셀 비교로 자동화.*
- **headless/offscreen rendering**: 창 안 띄우고 GPU로 그려서 결과만 빼오기. → *눈으로 안 봐도 그림이 나오게.*
- **mutation testing / mutation score**: 일부러 코드에 작은 버그를 심어("mutant") 테스트가 그걸 잡나 본다. 잡으면 "killed". score = 죽인 수 / 전체. → *"내 테스트가 진짜 일하나?"를 시험하는 테스트의 테스트.* (지금은 안 함, 나중 단계)

## 2. 지금 어디까지 와 있나

- ✅ **이미 있음**: CPU 함수 28개 자동 테스트(타이머·수학·상태머신 등) — `ctest` 한 방에 28개 다 PASS 확인됨.
- ✅ **이미 있음**: 정답 화면 3장(golden image) 찍어둠(전체화면 / UI끈것 / 하늘만). 단 *아직 자동 비교는 안 붙음*.
- 🔜 **이번 계획**: 테스트를 더 늘리고(아래 A), 정답 화면 자동 비교를 붙이고(B), GPU 단을 검사(C).

## 3. 계획을 단계별로 쉽게

### Phase A — CPU 함수 자동 테스트 더 만들기 (제일 쉽고 안전)
GPU(그래픽카드) 안 켜고, **순수 함수에 값 넣고 결과 확인**만 한다. 가장 빠르고 안 깨진다.
- 무엇을 추가? 씬 트리(부모-자식 관계)·연출 재생 순서·입력 처리·타이머·폰트 글자·머티리얼 6가지.
- 비유: *"이 함수에 이거 넣으면 저게 나와야 해"를 로그 대신 코드로 박는 작업 6개.*
- **여기에 + 진단 코드 테스트(A3)**: 우리 엔진엔 이미 "GL 상태를 찍어보는 진단 도구"가 있다. 그게 *제대로 된 값을 돌려주는지*를 CPU 테스트로 잠근다. (자세한 건 §4)

### Phase B — 정답 화면 자동 비교 (golden image)
이미 찍어둔 정답 화면 3장과, 지금 빌드가 그린 화면을 **자동으로 비교**한다.
- 어떻게? 게임을 "캡처 모드"로 잠깐 돌려 화면 3장 뽑고 → 정답과 픽셀 비교 → 다르면 FAIL + 차이 그림 저장.
- **허용오차(tolerance)**: 똑같길 바라지만 GPU 미세 차이가 있을 수 있어, "**전체 픽셀의 5%까지 달라도 통과**"로 둔다. (`pixelmatch` 라이브러리 사용)
- 꼭 지킬 규칙: **정답 화면을 기계가 멋대로 덮어쓰면 안 됨** — 화면을 일부러 바꿨을 때만 *사람이 보고* 새 정답으로 교체. (안 그러면 "버그 난 화면"을 정답이라고 박아버림.)
- 비유: *"화면 똑같지?"를 눈 대신 픽셀 비교로. 단 정답 갱신은 꼭 사람이 승인.*

### Phase C — GPU 단 검사 (가장 값짐, 하지만 GPU 필요)
창 안 띄우고(headless) GPU를 켜서, 눈으로 안 보이는 문제를 잡는다.
- **C-1 셰이더가 진짜 링크되나** ★가장 중요: 우리 셰이더는 빌드는 통과하는데 **macOS 실행 때만 조용히 깨져 화면이 투명**해지는 함정이 있었다(과거 여러 번). 모든 셰이더를 실제로 GPU에 올려 "링크 성공?"을 자동 확인 → 이 함정을 빌드 단계에서 잡는다.
- **C-2 그리기 설정 캐시**: "알파 블렌딩" 같은 GPU 설정이 캐시 때문에 안 먹던 버그를 검사.
- **C-3 왕복 검사**: 데이터를 GPU에 올렸다 다시 빼와서 그대로인지.
- **C-4 상태 누수**: 한 번 그린 뒤 GPU 설정이 *다음 그리기로 새는지* 검사 — 골든 이미지가 못 잡는 사각지대.
- 비유: *"빌드는 됐는데 왜 화면이 안 나와?"를 LLDB로 한참 뒤지던 걸, 자동 검문소로 만든 것.*

### Phase D — 테스트의 테스트 (나중에, 지금 안 함)
mutation testing 으로 "내 테스트가 진짜 버그를 잡나" 시험 + 퍼징(이상한 입력 마구 넣기). 무거운 도구라 **미래 작업으로만 기록**.

## 4. "진단 도구를 테스트 판정 기준으로 쓴다"는 게 무슨 말? (표준어: 화이트박스 상태 검증)

우리 엔진엔 이미 **GL 상태를 구조체로 찍어주는 진단 코드**(`CaptureGLState` 등)가 있다. 두 가지로 쓰인다:
1. **그 진단 코드가 맞게 동작하나**(A3, CPU): "상태 A와 B를 주면 *차이*를 바르게 뽑나" 같은 순수 함수 테스트.
2. **그 진단을 *판정 기준*으로 재사용**(C-4): 화면(픽셀)이 아니라 **내부 GL 상태**를 찍어 before/after 비교 → "설정이 샜다"를 직접 판정.

쉽게: *골든 이미지는 "겉(픽셀)"을 보고, 진단 기반 검사는 "속(GPU 상태)"을 본다.* 둘은 **서로 대체가 아니라 보완** — 겉이 같아도 속이 새면 진단이 잡고, 속이 멀쩡해도 색이 틀리면 골든이 잡는다.

⚠ 한 가지 솔직한 한계: "로그 글자를 긁어서 판정"하는 방식은 **안 쓴다**(전역 로거라 테스트끼리 꼬이고, 한글 산문이라 부서지기 쉬움). 대신 **함수가 돌려주는 구조화된 값**으로 판정한다.

---

## 5. 왜 이 순서인가 (checkpoint = 안전하게 끊는 지점)

`A(쉬운 CPU) → 진단 CPU(A3) → [여기서 한 번 끊기] → B(골든) → C(GPU)`

- **쉬운 것·안 깨지는 것부터.** CPU 테스트는 GPU 없이 빨라서 먼저. 그게 다 초록불(green)이면 안심하고 다음.
- **성격이 바뀌는 지점에서 끊는다.** "CPU만" 하다가 "GPU 켜야" 하는 순간은 환경이 확 달라지므로, 거기서 한 번 매듭(checkpoint)짓고 넘어간다.
- 비유: *등산로 대피소. 한 구간 무사 통과(green)할 때마다 짐 정리하고 다음 구간.*

---

## 6. 한 장 요약

1. **테스트 = 로그/LLDB로 하던 확인을 기계가 매번 자동으로.**
2. **Phase A**: CPU 함수 자동 확인 더 만들기 (쉬움, 먼저).
3. **Phase B**: 정답 화면 자동 비교 (5% 허용오차, 정답 갱신은 사람 승인).
4. **Phase C**: GPU 켜고 "셰이더 링크·상태 누수" 검사 (가장 값짐).
5. **Phase D**: 테스트가 진짜 일하나 시험 (나중).
6. 순서는 **쉬운 것·안 깨지는 것 먼저, 성격 바뀌는 데서 끊기.**

정식 설계(시그니처·경로·결정 근거)는 `doc/superpowers/specs/2026-06-27-test-expansion-design.md`, 용어 표준 매핑은 그 §0.1.
