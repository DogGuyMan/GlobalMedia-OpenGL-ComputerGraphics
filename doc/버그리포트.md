# Slang 버그 리포트 — PCB 스테이지 바닥 완전 투명 (varying 이름 불일치 링크 실패)

> 작성: 2026-06-21 · 컨텍스트: Phase 2.5 (phong.slang UBO 화 + phong_lighting 모듈 단일화) 육안 게이트 중 발생.
> 결론: **2개 버그** — (A) Slang GLSL inter-stage varying 이름 불일치로 런타임 GL 링크 실패, (B) overlay staleness.
> 둘 다 해결 후 PCB 정상 조명 확인 (사용자 육안 OK).

---

## 1. 증상

PCB 스테이지 모델(바닥/회로기판)을 loose `phong_albedo.fs` 에서 **Slang UBO phong (`phong.vs`/`phong.fs`)** 으로 전환하자,
**PCB 가 화면에서 완전히 사라짐 (그냥 투명, 배경이 비쳐 보임).**

- 변환/위치 오류처럼 "찌그러짐/이동" 이 아니라 **아예 안 그려짐**.
- simple.slang(불릿)은 같은 UBO 경로로 정상 작동 중 (Phase 2 R1 OK).

---

## 2. 진단 타임라인 (배제법)

| 가설 | 검증 방법 | 결과 |
|---|---|---|
| 변환(행렬) 오류로 off-screen | 생성 `phong.vs` 의 `gl_Position` 계산을 정상 `simple.vs` 와 비교 | X 동일 (row-vector x row_major). 변환 정상 |
| 셰이더 GLSL 문법 오류 | `glslangValidator -S vert/frag` 로 생성 GLSL 검증 | X 통과 (셋 다 clean) |
| VS-FS varying location 불일치 | 생성물 grep `layout(location=...)` | X location 은 0/1 로 일치 |
| 프로그램 생성 실패 (런타임) | **앱 백그라운드 기동 -> GL 진단 로그 수확** | O **여기서 발견** |

**결정적 로그 (런타임 GL):**
```
[error] 프로그램 링크 실패:
WARNING: Output of vertex shader 'entryPointParam_vsMain_wPos_0' not read by fragment shader
ERROR: Input of fragment shader 'input_wNormal_0' not written by vertex shader
ERROR: Input of fragment shader 'input_wPos_0' not written by vertex shader
[error] CreateProgram: 셰이더 컴파일/링크 실패 - key 'stage_phong_albedo'
```

-> **컴파일은 통과, 런타임 GL *링크* 실패.** VS 출력 varying 이름은 `entryPointParam_vsMain_wPos_0`,
FS 입력 varying 이름은 `input_wPos_0` — **이름이 다르다.**

---

## 3. 근본 원인

### 버그 A — Slang GLSL inter-stage varying 이름 불일치 (핵심)

1. **Slang 은 stage 별로 varying 을 다른 규약으로 명명**한다:
   - vertex out -> `entryPointParam_<entry>_<field>_N`
   - fragment in -> `input_<field>_N`
2. 우리 툴체인은 **VS 와 FS 를 *각각 별도 slangc 호출*** 로 컴파일한다 (`-entry vsMain` 1회, `-entry fsMain` 1회).
   각 호출이 자기 stage 관점으로 varying 을 명명하므로 **두 이름이 조정되지 않는다**.
   (slangc 의 GLSL 다출력 단일호출은 미지원 — `-o` 다중 결속 불가. SPIR-V 만 지원.)
3. Slang 은 **location 기반 매칭**(Vulkan/SPIR-V 정통)을 가정한다. 그래서 이름이 달라도 무방 — *대부분의 타깃에선*.
4. 그러나 **macOS OpenGL 4.1 은 non-separable program 의 varying 을 location 이 아니라 *이름* 으로 매칭**한다.
   -> VS-out 이름 != FS-in 이름 -> 링크 실패 -> `glCreateProgram` 결과 무효(program=0).
5. `mesh_pass_processor` 는 `program == nullptr` 인 DrawCommand 를 **skip** -> PCB 가 안 그려짐 = **투명**.

**왜 simple.slang 은 무사했나:** simple 은 unlit(단색)이라 **inter-stage varying 이 0개** (FS 가 VS 출력을 안 받음, UBO 색만 출력).
varying 이 없으니 이름 불일치도 없어 링크 성공. **phong 이 varying 을 가진 *첫* 셰이더**라 이 함정이 처음 드러났다.

**왜 glslangValidator 는 못 잡았나:** glslang 은 셰이더를 *개별* 검증(문법/타입) — VS/FS 를 *링크* 하지 않으므로
cross-stage 이름 매칭을 검사하지 않는다. 링크 실패는 *실제 GL 컨텍스트에서 두 셰이더를 link 할 때* 만 드러난다.

### 버그 B — overlay staleness (부차)

- 생성 셰이더는 `slang_generated/shaders/` 에 떨어지고, **POST_BUILD** 가 실행파일 옆 `resources/shaders/` 로 복사(overlay).
- `POST_BUILD` 는 **타겟이 relink 될 때만 실행**된다. 셰이더만 바뀌면 `_MyApp_` 는 relink 안 돼 **복사가 누락** ->
  런타임이 *없는/낡은* `resources/shaders/phong.vs` 를 로드 -> "셰이더 컴파일 실패 (빈 InfoLog)".
- 진단 중 이걸 varying 버그로 오인할 뻔했으나, **InfoLog 가 비어있음 + 파일 부재** 로 식별.

## 4. 해결

### 4-1. Python post-process 로 varying 이름 정규화 (버그 A)

CMake `string(REGEX)` 텍스트 처리를 **Python 스크립트로 이관** (정밀한 word-boundary 치환 + 책임 분리).
[`cmake/slang_compile.py`](../cmake/slang_compile.py) (Slang 파이프라인 단일 스크립트 — slangc 호출 + post-process + reflection + depfile):

- 기존 410 변환 3종(`#version`, `layout(binding)`, `layout(row_major) buffer`) + **varying 정규화 1종**.
- **stage-aware**: vertex 의 `out` / fragment 의 `in` varying 만 -> 동일한 location 기반 정규명 `_slangVaryN` 으로 치환.
  - VS-out 의 location N 과 FS-in 의 location N 이 *같은 이름* (`_slangVaryN`) 이 되어 macOS 이름매칭 성립.
  - vertex 의 `in`(attribute) / fragment 의 `out`(color) 는 location 매칭이므로 건드리지 않음 (in/out location 충돌 회피).
- (구 `cmake/SlangPostProcess410.cmake` 는 삭제 — Python 으로 대체.)

치환 결과:
```glsl
// phong.vs:  out vec3 _slangVary0;  out vec3 _slangVary1;
// phong.fs:  in  vec3 _slangVary0;  in  vec3 _slangVary1;   // <- 이름 일치 -> 링크 성공
```

> 참고: 선행 underscore `_slangVaryN` 은 glslang + Apple GL 둘 다 허용 (`__` 더블/`gl_` 만 예약).

### 4-2. Slang.cmake 모듈 import 정식화 (병행)

[`cmake/Slang.cmake`](../cmake/Slang.cmake) `sjh_compile_slang`/`sjh_reflect_slang`:
- **`-I <input.slang 디렉토리>`** — `import phong_lighting` 모듈 해결 (sibling .slang).
- **sibling `*.slang` 을 DEPENDS 에** — `import` 대상(모듈 파일) 편집 시 소비 셰이더 재컴파일 (staleness 회피).
- post-process 명령을 `cmake -P` -> `python3 slang_postprocess_410.py --in --out --stage` 로 전환 (+ python3 find/가드).

### 4-3. overlay 를 매-빌드 COMMAND 로 (버그 B)

[`apps/_MyApp_/CMakeLists.txt`](../apps/_MyApp_/CMakeLists.txt):
- 생성 셰이더 -> `resources/shaders` overlay 를 **`_MyApp__shaders` 타겟의 COMMAND** 로 이동
  (custom target 은 매 빌드 실행 -> 셰이더만 바뀌어도 복사 보장. POST_BUILD overlay 삭제).
- **함정**: dest 에 `$<TARGET_FILE_DIR:_MyApp_>` 쓰면 `_shaders -> _MyApp_` 의존 발생 -> `_MyApp_ -> _shaders` 와 *사이클*.
  -> 평범한 경로 `${CMAKE_CURRENT_BINARY_DIR}/resources/shaders` 로 끊음 (exe 거주지와 동일).
- `_MyApp_` 의 resources POST_BUILD 복사는 `copy_directory` 가 *머지* 라 생성 `phong.*` 를 지우지 않음.

## 6. 교훈 / 예방

1. **Slang->GLSL 분리 컴파일 + macOS GL = varying 이름 매칭 함정.** Slang 은 location 매칭(Vulkan)을 가정하나
   Apple GL 4.1 은 non-separable program 에서 *이름* 매칭. varying 가진 *모든* 셰이더가 영향 -> post-process 정규화가 SSOT.
2. **glslangValidator 통과 != 링크 성공.** 개별 검증은 cross-stage 이름 매칭을 못 본다. *실제 GL 링크* 로만 드러남
   -> 신규 varying 셰이더는 **반드시 런타임 기동 로그**로 확인.
3. **"투명/사라짐" 은 거의 항상 *안 그려짐*** (off-screen 또는 program=null). 검정(unlit)과 구분하려면 GL 진단 로그 1순위.
4. **CMake 텍스트 변환은 Python 으로.** `string(REGEX)` 는 부분-토큰 오손 위험 + 클렁키. CMake=오케스트레이션, 변환=스크립트.
5. **POST_BUILD 는 relink 시에만.** 부산물(셰이더) 복사는 custom target COMMAND 로 (매 빌드). 단 generator expression
   으로 dest 잡으면 사이클 — 평범한 경로 사용.

# Render GL-State 통합 버그 리포트 — Transparent 알파 무시 (healthbar 조각 사라짐 + shadow 새까맘)

> 작성: 2026-06-21 · 컨텍스트: render GL-state 권위 통합 Phase A (D-RS-1/D-RS-5, `PipelineStateSetter` -> `DeviceContext::ApplyPipelineState` 흡수 + 명령형 `SetDepthTest/SetBlend` 제거) 직후 육안 게이트.
> 결론: **blend func 미초기화** — 캐시 기본값과 GL 실제 초기값 불일치를 off->on 전이에서 강제하지 않아 알파 블렌딩이 replace 로 동작. 수정 후 정상 (사용자 육안 OK).

## 1. 증상
- **healthbar**: 내부 5조각 칸막이가 사라지고 하나로 합쳐진 단색 Bar.
- **shadow (EntityShadow.png 데칼)**: 알파 falloff 가 무시되고 **완전 새까만** 블롭/사각.
- 공통점: 둘 다 `Pass::Kind::Transparent`(blend on) + 알파 의존 출력인데 **알파가 전혀 적용 안 됨**.

## 2. 진단 (배제법)
| 가설 | 검증 | 결과 |
|---|---|---|
| uniform 미업로드(uSegmentCount/baseColor) | WorldMesh loose 경로 `PropertyBlockSetter::Set` 보존 확인 (mesh_pass_processor.cpp:199) | X 업로드 정상 |
| Pass 가 Transparent 아님 | HealthBarFactory.cpp:66 / PlayerBuilder.cpp:210 `SetPass(Transparent)` 확인 | X 둘 다 Transparent (blend on 기대) |
| **blend func 미설정** | `ApplyBlend` 의 `SetBlendFunc` dirty-check 추적 | O **여기서 발견** |

## 3. 근본 원인 — blend func 캐시 기본값 vs GL 실제 초기값 불일치
1. GL 의 `glBlendFunc` 기본값 = **`(GL_ONE, GL_ZERO)`** (= src*1 + dst*0 = replace, 알파 무시).
2. 구 `DeviceContext::BeginFrame` 은 매 프레임 `SetBlend(true, GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA)` 로 **`glBlendFunc` 을 명시 호출**해 GL func 을 SRC_ALPHA/ONE_MINUS 로 박아뒀다. PipelineStateSetter 의 dirty-cache 가 func 설정을 skip 해도 GL 엔 이미 올바른 func 이 있어 **무해 (잠복 버그 마스킹)**.
3. Phase A(D-RS-5) 의 새 `BeginFrame` 은 `ApplyPipelineState(Opaque)` 만 호출 — Opaque 는 `BlendEnable=false` 라 `ApplyBlend` 가 `glBlendFunc` 을 **안 부른다** (`if (want.BlendEnable) SetBlendFunc`).
4. 이후 Transparent 객체가 blend 를 켤 때, `SetBlendFunc` 의 dirty-check 가 `mLast.BlendSrc/Dst`(기본값 SRC_ALPHA/ONE_MINUS) == want 라고 판단해 **`glBlendFunc` 을 영영 skip**.
5. 결과: GL blend 는 enable 됐으나 func 은 기본 `(ONE,ZERO)` 잔재 -> **알파 블렌딩이 replace 처럼 동작** -> healthbar 간격(alpha=0) 픽셀이 불투명하게 바 색을 쓰고(=칸 사라짐), shadow 가 불투명 검정으로 출력.

**핵심**: dirty-cache 의 초기 `mLast.BlendSrc/Dst`(SRC_ALPHA/ONE_MINUS)가 GL 실제 초기값(ONE/ZERO)과 **불일치**한데, blend off->on 전이에서 func 을 강제하지 않아 캐시가 "이미 일치"로 오판.

## 4. 해결
[`src/render/device_context.cpp`](../src/render/device_context.cpp) `ApplyBlend` — **blend off->on 전이(또는 `InvalidateStateCache` 후 첫 enable)에서 `glBlendFunc` 을 무조건 적용**:
```cpp
const bool prevEnabled = initialized && last.BlendEnable;   // 직전에 확실히 켜져 있었나
SetBlendToggle(want.BlendEnable, last, initialized);
if (!want.BlendEnable) return;
if (!prevEnabled) {            // off->on / invalidate 후 첫 enable - GL func 미확정 -> 무조건 적용
    glBlendFunc(want.BlendSrc, want.BlendDst);
    last.BlendSrc = want.BlendSrc; last.BlendDst = want.BlendDst;
} else {                       // 연속 blend - func 바뀐 경우만 (dirty-check)
    SetBlendFunc(want.BlendSrc, want.BlendDst, last, initialized);
}
```
ScreenQuadStage 의 2+ 소스 alpha 합성(Screen state + `BlendEnable=true`)도 동일 경로로 해결.

## 5. 교훈 / 예방
1. **dirty-cache 의 초기값은 GL 실제 초기 상태와 일치시키거나, 첫 적용을 강제하라.** GL 기본 blendFunc=`(ONE,ZERO)` ≠ 캐시 기본 `(SRC_ALPHA,ONE_MINUS)`. 불일치 상태 변수는 off->on 전이에서 반드시 강제.
2. **조건부 적용 state(blend func 은 `if(BlendEnable)` 게이트)는 toggle 과 함께 캐시 desync 위험.** 토글이 켜질 때 종속 state(func)도 함께 보장해야 함.
3. **명령형 초기화에 의존하던 잠복 버그는 그 초기화를 제거할 때 드러난다.** 구 BeginFrame 의 `SetBlend(true,...)` 가 마스킹하던 것을 D-RS-5 가 걷어내며 표면화.
4. 정본 설계: spec `doc/superpowers/specs/2026-06-21-render-state-ownership-consolidation-design.md` / plan `doc/superpowers/plans/2026-06-21-render-state-consolidation.md`.

# Slang Phase 3 버그 리포트 — Slang sampler global `_N` 접미사 (텍스처 오염)

> 작성: 2026-06-21 · 컨텍스트: Phase 3 Slice 1-1 (`simple_texture.slang` = 첫 *textured* Slang 셰이더 UBO화) 육안 게이트.
> 결론: Slang 이 sampler global 에 `_0` 접미사를 붙여(`uTex` -> `uTex_0`) 엔진의 author-이름 바인딩과 불일치 → 텍스처 미바인딩 → 직전 unit 잔재 샘플(오염). post-process 정규화로 해결.

## 1. 증상
ground 데칼(발밑 그림자=EntityShadow.png / 피격범위=Circle_albedo.png)이 **둘 다 엉뚱한 단일 텍스처로 오염** (각자 텍스처 대신 직전 draw 의 텍스처가 보임).

## 2. 근본 원인
- 생성 `simple_texture.fs`: `uniform sampler2D uTex_0;` — **Slang 이 sampler global 에 `_N`(0) 접미사**.
- 엔진 `PropertyBlockSetter` 는 sampler 를 *author 이름* (`uTex` = `Material.Properties.Textures` 키)으로 바인딩 → program active uniform `uTex_0` 와 매칭 실패 → `glBindTexture`/`glUniform1i` 미실행 → 샘플러가 **unit 0 의 직전 잔재 텍스처**를 샘플 → 둘 다 같은 오염 텍스처.
- UBO 블록(`block_MaterialBlock_0`)은 `Program::BuildUniformBlocks` 가 별도 정규화("MaterialBlock")해서 무사 → baseColor/tint 는 정상. **sampler 만 정규화 경로 밖** (textureless 였던 simple/phong 엔 안 드러남 — `simple_texture` 가 첫 textured Slang 셰이더).
- (VS 입력 location 은 `[[vk::location(2)]]` 로 정상 → `layout(location=2) in vec2` 확인. UV 문제 아님.)

## 3. 해결
[`scripts/slang_compile.py`](../scripts/slang_compile.py) post-process 에 **`normalize_sampler_names`** 추가 (varying 정규화와 동형):
- `uniform sampler\w+ <name>_<N>;` 매칭 → `<name>_<N>` 을 선언+사용처 word-boundary 치환으로 `<name>` 복원.
- `post_process_glsl_410` 5단계로 편입 (모든 slang 셰이더 sampler 에 일반 적용 → 향후 textured 슬라이스 자동 혜택).

## 4. 교훈 / 예방
1. **Slang global(sampler) 은 `_N` 접미사를 받는다.** 엔진이 *이름* 으로 바인딩하는 자원(sampler)은 post-process 정규화 필수. UBO 블록은 엔진이 따로 정규화하나 sampler 는 그 경로 밖.
2. **"텍스처 오염(엉뚱한 단일 텍스처)" = 샘플러 미바인딩 + unit 0 잔재.** "UV 깨짐"(텍스처는 맞으나 왜곡)과 구분 — 오염은 바인딩 실패, 왜곡은 location/UV.
3. varying `_slangVaryN` 함정과 **동일 계열** (Slang→GLSL 이름 vs macOS GL 매칭) — textured 셰이더마다 재발 가능했으나 post-process 일반화로 차단.

# 간헐 SIGSEGV 버그 리포트 — Actor::Update 순회 중 dangling Actor (FX 스폰이 트리 무효화)

> 작성: 2026-06-21 · 컨텍스트: 게임 시작 직후 R 궁극기(회전 히트스캔 레이저) 사용 시 간헐적 크래시. 핸드오프 `doc/handoffs/2026-06-21-actor-update-crash-handoff.md` 기반 systematic-debugging.
> 결론: **순회 도중 FX 스폰(`AddChild`)으로 `mChildren` 재할당 → 라이브 iterator 무효화(use-after-free)**. observer/defer 로 스폰을 순회 밖으로 미뤄 해결.

---

## 1. 증상
- 게임 시작하자마자 즉시 'R'(궁극기) 사용 시 간헐적 `EXC_BAD_ACCESS (SIGSEGV)`. 타이밍 의존.
- 크래시 리포트 2회 스택 완전 동일 — 전부 `scene/Stage/FSM Update` 경로, **`src/render/`/Effekseer/GL 프레임 0개** (렌더 아닌 Update 단계).
- 직전 로그: `[Wave 1] Enemy spawned ...` → 적 스폰 직후.

```
0  SJH::Scene::Actor::Update(float) + 28      <- 폴트 (this = 쓰레기 작은 주소, far = this+0x84)
1  SJH::Scene::Actor::Update(float) + 292      <- 자식 순회 (B.mChildren)
2  SJH::Scene::Actor::Update(float) + 292      <- 자식 순회 (root.mChildren)
3  SJH::Scene::Director::Update(float) + 32
4  CombatPlayState::OnUpdate(...) + 56
...
```
- 레지스터: `x8 = 0x66828`(this), `far = 0x668ac`(this+0x84) → **`this` 자체가 손상된 Actor 포인터**.
- 스레드 컨텍스트에 `vector<unique_ptr<Actor>>` 심볼 노출 → `Actor::Update` 가 자식 컬렉션 순회 중임을 시사.

---

## 2. 진단 (배제법 + 정적 추적)

| 가설 | 검증 | 결과 |
|---|---|---|
| Phase A render GL-state 통합이 원인 | 스택에 `src/render/` 프레임 유무 + Phase A 변경 범위 확인 | X 무관 (스택 0개, Phase A 는 `scene/Actor` 미접근) |
| 적 제거(`RemoveChild`)가 순회 중 발생 | `WaveController::OnEnemyDeath`/`SweepDespawned` 추적 | X **제거는 전부 defer 됨** (enqueue → Step/Update 밖 sweep) |

**결정적 코드 체인 (전부 정적 확인):**
1. `main.cpp:180` — `mFxRoot = dir.Root().AddChild(...)` → **fxRoot 는 root 의 직계 자식** = 스택 frame 1(B)와 일치.

---

## 3. 근본 원인 — 설계 비대칭 (제거는 defer, 스폰은 즉시)

이 코드베이스는 **콜백/순회 도중 트리·body 변경 금지, sweep 으로 defer** 라는 컨벤션을 일관 적용한다 (Box2D `b2World::Step` 잠금 중 body 변경 금지와 동형):
- 적 제거: `OnEnemyDeath`(enqueue) → `SweepDespawned`(Step 밖 `RemoveChild`).
- 단발 FX 제거: `AutoDespawnOnFinish`(mark) → `SweepFinishedChildren`(Update 밖 `RemoveChild`).

그러나 **데미지 seam 의 FX *스폰(AddChild)* 은 defer 되지 않고 순회 도중 즉시 실행**됐다. 이것이 진짜 버그.

- **왜 R 전용인가:** UltimateLaser 만이 (a) fxRoot 의 자식이면서 (b) 순회 도중 `RaycastAll`+`DoDamaged` 로 즉시 다수 적을 타격하는 유일한 데미지원. 일반 총알은 Root 직속 별도 actor + Box2D 접촉(`Director::Update` *앞* 의 Step)이라, 접촉 데미지의 `onHitFx` 도 순회 전 append → 무사. 레이저만 fxRoot 서브트리 *안* 에서 데미지를 줘 그 결과 FX 가 fxRoot 자기 자신에 re-entrant `AddChild`.
- **왜 간헐적인가:** ①그 프레임 레이가 적에 실제 명중 ②`push_back` 이 마침 재할당 유발(capacity 의존) ③순회에 남은 다음 자식 존재 — 3조건 동시. "시작 직후 즉시 R" + "Wave1 스폰 직후" 가 ①확률 최대화.
- **왜 안 잡혔나:** 제거 경로는 이미 철저히 defer 돼 있어 모두가 "트리 변경은 defer 됨" 으로 믿었으나, *스폰* 방향에 같은 규율이 빠져 있었다.

---

## 4. 해결 — 왜 index 순회를 버리고 observer/defer 로 갔나

### 후보 A — `Actor::Update` index 순회로 하드닝
`for (auto& child : mChildren)` → `for (size_t i=0; i<mChildren.size(); ++i) mChildren[i]->Update(dt)`.
- 장점: 한 곳(`src/scene/actor.cpp`)에서 **전체 클래스**(총알/FX/미래 코드) 차단. 재할당돼도 매 회 현재 버퍼 재인덱싱 → 안전.
- 단점(사용자 판단): "Update 중 트리 변경 금지" 컨벤션을 *명시적으로 강제*하지 않고 graceful degrade 로 흡수 → 설계 의도가 흐려질 수 있음. (성능은 무관 — index 순회는 busy-wait 아님, 자식당 포인터 산술 1~2개 추가뿐.)

### 후보 B (채택) — observer/defer-FX
FX 스폰을 **기존 제거-defer 컨벤션과 대칭**으로 미룬다: seam 은 즉시 `AddChild` 대신 큐에 적재(notify)하고, main 루프가 `Director::Update` *밖* 에서 flush.
- **채택 이유:** 이 코드베이스의 정통 패턴(`mOnDeath` observer + `SweepDespawned`, `AutoDespawnOnFinish` + `SweepFinishedChildren`)과 **완전 동형**. "순회 도중 트리 변경 0" 이라는 불변식을 *유지*하므로 `Actor::Update` 의 range-for 가 본래 가정대로 안전해진다 — 컨벤션을 우회하지 않고 *준수*.
- 비용: 작은 vector push/drain (무시 가능). FX 가 1프레임(16ms) 늦게 등장 — 기존 sweep 들과 동일하게 지각 불가.

> 즉 후보 A 는 "프리미티브를 방탄으로", 후보 B 는 "컨벤션을 일관되게". 사용자는 *설계 일관성*(observer)을 택함.

스폰 파사드 2종을 **즉시 `AddChild` → 큐 적재 + `FlushSpawns()`(순회 밖 drain)** 로 전환.

| # | 파일 | 변경 |
|---|---|---|
| 1 | `apps/_MyApp_/src/Spawns/VfxFacade.cpp` | `VFX::Spawn` → `gPending` 큐 적재. `FlushSpawns()` 추가 |

| 5 | `apps/_MyApp_/main.cpp` | `Director::Update` 종료 후(`SweepFinishedChildren` 직전) 양 큐 flush |

**핵심 코드 (VfxFacade.cpp — WorldText 도 동형):**
```cpp
struct PendingVfx { std::string key; vmath::vec3 pos; float yaw; };  // key 값 보유 (호출측 수명 무관)
std::vector<PendingVfx> gPending;

void Spawn(const char* key, const vmath::vec3& pos, float yaw) {
    if (gFxRoot == nullptr || gVfx == nullptr) return;
    gPending.push_back(PendingVfx{key, pos, yaw});   // [!] 즉시 AddChild 금지 — 적재만
}

void FlushSpawns() {                                  // Director::Update 밖에서 1회/프레임 호출
    if (gPending.empty()) return;
    std::vector<PendingVfx> batch;
    batch.swap(gPending);                             // 재진입 안전 (flush 중 새 Spawn 은 다음 프레임)
    if (gFxRoot == nullptr || gVfx == nullptr) return;
    for (const auto& p : batch) {
        SJH::Effect* fx = SJH::ResourceRegistry::Get().FindEffect(p.key.c_str());
        Spawns::SpawnVfxInstance(*gFxRoot, gVfx, fx, p.pos, p.yaw);
    }
}
```
**main.cpp (flush 호출):**
```cpp
if (mStageFsm) mStageFsm->Update(dt);   // ← 내부 Director::Update (순회 = 큐 적재)
...
TopdownShooter::VFX::FlushSpawns();        // 순회 밖 = AddChild 안전
TopdownShooter::WorldText::FlushSpawns();
if (mFxRoot) TopdownShooter::Spawns::SweepFinishedChildren(*mFxRoot);  // 그 후 제거 sweep
```

설계 성질:
- 흐름: `Director::Update`(순회→적재) → flush(`AddChild`, 순회 밖) → sweep(제거). **순회 중 트리 변경 0**.
- swap-drain 으로 flush 재진입 안전. 모든 호출처가 fire-and-forget seam(반환값 미검사)이라 1프레임 defer 가 투명. 키는 정적 리터럴(`"hit"`/`"dust"`/`"gunshoot"`).
- 부수효과: dust(`onMoveFx`, 플레이어 이동=순회 중 스폰)도 같은 잠복 크래시였는데 함께 해소. UltimateLaser 자체의 `fxRoot->AddChild`(R 입력 핸들러=순회 *전*)는 안전하므로 미변경.

## 6. 교훈 / 예방
1. **순회 도중 트리 변경 금지 컨벤션은 *제거*뿐 아니라 *스폰(AddChild)* 에도 똑같이 적용해야 한다.** 한 방향만 defer 하면 비대칭 잠복 버그. Box2D Step 잠금 패턴과 동일 — 콜백/순회 중 구조 변경은 enqueue, 실제 변경은 밖에서.
2. **`Actor::Update` 의 range-for 는 `mChildren` 변경에 무방비.** 컨벤션(defer)으로 불변식을 지키거나, 정 안되면 index 순회로 하드닝. 둘 중 하나는 필요.
3. **"순회 중 component 가 부모/조상 트리를 건드리는가" 를 의심하라.** 특히 *fxRoot 서브트리 안* 의 component 가 *fxRoot 자신* 에 spawn 하는 re-entrant 경로 (UltimateLaser).
4. **간헐 크래시 + 작은 쓰레기 `this` + vector 심볼 = use-after-free 순회.** 스택의 재귀 깊이로 손상 컬렉션의 트리 위치를 특정 가능(frame 1 = root 직계 자식 = fxRoot).
5. 동일 계열 메모리: Box2D Step 잠금 중 body 변경 defer (`box2d_step_lock_defer_body_changes`).

# Slang Phase 3 버그 리포트 — Slang 배열 brace-init (GLSL 420) macOS 410 거부 (sharpening/sobel 누락)

> 작성: 2026-06-21 · 컨텍스트: Phase 3 Slice 2 postfx 일괄 전환 후 ImGui 에서 sharpening/sobel 누락 + 매핑 밀림.
> 결론: Slang 이 배열을 `타입[N] = {...}`(GLSL420 brace-init)로 출력 → macOS GL410 런타임 거부 → program=null → 패스 누락.

## 1. 증상
- ImGui PostFX 에서 sharpening + sobel 이 사라지고, 나머지 라벨이 +1 밀려 엉뚱한 효과를 제어("정합" 붕괴).
- 빌드/glslangValidator 는 통과(=컴파일 단계 무에러).

## 2. 두 갈래 원인
### A. 정합 붕괴 (positional zip off-by-one)
- 소비자가 `debugEntries.push_back({POSTFX_PROGRAM_CONFIGS[i].Name, result.PassComponents[i]})` 로 **인덱스 zip**.
- `BuildPostFXChain` 이 프로그램 로드 실패 패스를 `continue` 로 **건너뛰어** `PassComponents` 가 짧아짐 → 누락 지점부터 Name↔Component 가 1칸씩 밀림.
- **해결**: `render_pipeline.cpp` 의 3개 실패 경로가 `nullptr` placeholder 를 push → `PassComponents[i]`↔`configs[i]` 1:1 정렬 유지 (PostFXDebugLayer 의 `if(!Component) continue` 가 null 자연 skip).

### B. 로드 실패 근본 (배열 brace-init)
- 생성 GLSL 대조 (결정적 증거): **배열 리터럴 셰이더만 실패**.
  - `blurring.fs`(작동): offset 을 `cell * texel` **inline** 계산 - 배열 0.
  - `sharpening.fs`/`sobel.fs`(실패): `vec2 _S5[9] = {...}` + `const float _S6[9] = {...}` - **brace-init 배열**.
  - invert/gamma/grayscale/bloom: 배열 0 → 무사.
- `타입[N] = {...}` (brace 초기화) 는 **GLSL 420**(ARB_shading_language_420pack). macOS GL **410** 코어는 미지원 → `glCompileShader` 거부 → program=null.
- "sharpening 은 blur 와 커널만 다른데 왜?" → 커널 로직이 아니라 *초기화 문법* 차이. blur 는 inline, sharpening/sobel 은 배열 리터럴.
- 결정타: **구 hand-written `sharpening.fs` 는 `vec2 offsets[9] = vec2[](...)` 생성자**(GLSL 1.20+, 410 유효)를 썼음. Slang 이 동일 의미를 `{...}`(420)로 출력.

## 3. 해결 (B)
[`scripts/slang_compile.py`](../scripts/slang_compile.py) post-process 에 `normalize_array_initializers` 추가:
- `타입[N] = {...}` → `타입[N] = 타입[](...)` (GLSL410 배열 생성자, 구 hand-written 과 동일 형태).
- regex `\b(vec[234]|mat[234]|float|int|uint|bool)(\s+\w+\s*\[\d+\]\s*=\s*)\{([^{}]*)\}` → `\1\2\1[](\3)` (선행 const 등 한정자 보존, flat 초기화 가정).

## 4. 교훈 — Slang -> macOS GL410 3대 함정 (glslang 통과 ≠ GL 링크/컴파일)
1. **inter-stage varying 이름** (VS-out ≠ FS-in) → `_slangVaryN` 정규화.
2. **sampler global `_N` 접미사** (`uTex_0` ≠ author `uTex`) → `_N` strip.
3. **배열 brace-init `[N]={...}`** (GLSL420) → 배열 생성자 `[]()` 변환.
- 공통: 셋 다 빌드/glslangValidator 통과, **실제 macOS GL 런타임에서만** 드러남 → 신규 셰이더는 *앱 기동 GL 로그 + 육안* 필수. 셋 다 post-process(slang_compile.py)가 SSOT.
- 정합 교훈: positional zip 은 중간 누락에 취약 → 실패 시 placeholder 로 인덱스 정렬 유지 (또는 by-key 매핑).

# Phase C 버그 리포트 — lit(phong) 셰이더 암전 (UBO binding point 전역 충돌)

> 작성: 2026-06-21 · 컨텍스트: Phase C (PropertyBlockSetter/uniform_cache 모듈 삭제) 직후, 게임플레이 중 lit 씬이 *갑자기 검정* 으로 변하는 현상 보고.
> 결론: **UBO binding point 가 program-local 블록 인덱스로 배정돼 전역 충돌** — phong 의 LightBlock 이 GL 열거상 point 1 에 떨어졌고, simple 불릿의 DrawBlock(point 1)이 공유 LightBlock UBO 를 덮어써 phong 이 모델행렬을 조명 데이터로 읽음. 의미명 기반 전역 고정 binding point 로 해결.

---

## 1. 증상
- **lit(LightBlock UBO 의존 = phong) 셰이더만 갑자기 암전(검정).** unlit(simple/skybox/postfx)은 정상.
- 게임 시작 시점엔 정상(lit 밝음) → 특정 게임플레이 이벤트 후 암전 + **지속**(한 프레임 깜빡임 아님).
- 사용자 초기 보고: 트리거 후보 3종(마젠타 불릿 스폰 / Effekseer 파티클 / 마우스 좌클릭) — 어느 것인지 불확실.

## 2. 사고 방식 (추론 + 잘못된 가정의 교정)

### 2-1. 1차 의심 = 직전 변경(Phase C light_ubo) → diff 로 자가 배제
가장 먼저 *방금 내가 건드린* `light_ubo_uploader.cpp`(loose 경로 제거)를 의심. `git diff` 로 검토 → **UBO 패킹/BindTo UBO 경로는 한 줄도 안 바뀜**(loose 헬퍼/캐시만 삭제). phong 은 원래도 UBO 전용(loose `UNI_VIEW_POS` 소비자 0)이라 *행위 중립* → 직접 원인 아님으로 배제.

### 2-2. 2차 가설 = "광원 목록 비워짐" vs "binding point 충돌"
lit 만, 지속, 이벤트 트리거 → 두 후보로 좁힘:
- (a) 이벤트가 light 컴포넌트를 비활성/제거 → LightBlock 전부 0 → 암전.
- (b) 공유 LightBlock UBO 가 다른 자원에 덮어써짐(binding point 충돌).

### 2-3. ★ 잘못된 배제 (정직한 기록) — "충돌 불가" 라고 *추론* 했으나 가정이 틀림
binding point = `blockIndex`(program.cpp) 임을 보고, 각 셰이더의 ConstantBuffer 개수를 grep:
- phong = 4블록(Frame/Draw/Material + import LightBlock) → **"LightBlock = 4번째 = point 3"** 으로 추정.
- 그 외 전부 ≤3블록(0,1,2) → "point 3 을 쓰는 건 phong 뿐 → 충돌 불가" 로 **가설 (b)를 기각**.

**이 추론의 결함:** GL 의 `glGetActiveUniformBlock*` 열거 순서 = *선언 순서* 라고 **암묵 가정**했다. 실제 GL 열거 순서는 구현 정의(declaration order 보장 없음)다. 즉 "LightBlock=point 3" 은 검증되지 않은 가정이었다.

### 2-4. 방향 전환 — "추론으로 binding point 를 단정할 수 없다 → 런타임 실측"
binding point 의 실제 값은 *GL 이 정한다*. 코드 정독으로는 알 수 없음을 인정하고, **추측을 멈추고 런타임 증거**로 전환.

## 3. 증명 방법 — 변화-게이트 진단 로그 (스팸 최소)
세 가설을 한 빌드로 가르도록 `[DIAG-AMBER]` 태그 임시 로그 3종 삽입 (값이 *바뀔 때만* 출력):

| 위치 | 로그 | 가르는 가설 |
|---|---|---|
| `program.cpp` `BuildUniformBlocks` | `prog=N block='X' bindingPoint=P` (프로그램 생성 1회) | **실제 binding point 맵** + 이벤트 시 신규 프로그램 등장 |
| `light_ubo` `Update` | `light counts changed: dir/points/spots` | (a) 광원 비워짐 |
| `light_ubo` `BindTo` | `LightBlock bindingPoint=P sharedUbo=1/0` | LightBlock 결속 안정성 |

사용자에게 *빌드 → 재현 → `[DIAG-AMBER]` 라인 + 어느 트리거인지* 회신 요청. (GL 쿼리 의존 없이 작성해 진단 코드 자체의 빌드 리스크 0.)

## 4. 결정적 증거
```
[DIAG-AMBER] light counts changed: dir=1 points=0 spots=0   <- 광원 살아있음 (가설 a 기각)
[DIAG-AMBER] LightBlock prog=90 bindingPoint=1               <- LightBlock = point 3 이 아니라 point 1!!
```
+ 사용자 확인: **"마젠타 Bullet 이 사라지니 암전도 사라진다"** → 트리거 = 불릿.

→ 2-3 의 가정("LightBlock=3")이 **틀렸음이 실측으로 드러남**. LightBlock 은 GL 열거상 **point 1**. 그리고 simple 불릿의 DrawBlock 도 program-local 인덱스 1 = **point 1** → 충돌 성립. 가설 (b) 확정.

## 5. 근본 원인 — program-local 인덱스를 전역 binding point 로 사용
1. `Program::BuildUniformBlocks` 가 `blk.bindingPoint = blockIndex`(그 program 안에서 0,1,2,..) 로 배정 (구 D12).
2. 그러나 `glBindBufferBase(GL_UNIFORM_BUFFER, point, ubo)` 의 point 는 **전역 GL state** — 모든 program 이 공유.
3. GL 이 phong 의 LightBlock 을 열거 index **1** 로 → phong LightBlock = 전역 point 1. 공유 LightBlock UBO 가 `BindTo` 에서 point 1 에 결속됨.
4. simple 불릿(Frame/Draw/Material 3블록)의 DrawBlock = program-local index **1** = 전역 point 1.
5. 불릿 draw 시 `program->BindUniformBlocks()` 가 불릿의 DrawBlock UBO(모델행렬)를 **전역 point 1 에 BindBase** → **공유 LightBlock 결속을 덮어씀**.
6. 이후 phong draw → point 1 에서 *불릿의 모델행렬* 을 LightBlock(조명)으로 읽음 → 조명값 쓰레기/0 → **암전**. (불릿 없으면 point 1 을 덮는 자가 없어 정상.)

- **왜 lit 만:** point 1 을 *LightBlock 으로* 읽는 건 phong 뿐. 불릿 자신은 point 1 을 *DrawBlock 으로* 정상 사용(unlit 무영향).
- **왜 지속:** 불릿이 존재하는 한 매 프레임 `BindTo`(공유 결속) 직후 불릿 draw 가 다시 덮음.
- **왜 잠복했나:** 엄밀히는 Phase 2 의 `bindingPoint=blockIndex` 결함. Gate Bᴳ 에서 phong(LightBlock)+불릿(simple) 둘 다 UBO 가 되고, GL 이 LightBlock 을 하필 point 1(=흔한 DrawBlock 슬롯)에 배정하며 표면화. Phase C 와는 무관(직전 작업이라 의심받았을 뿐).

## 6. 해결 — 의미명 기반 전역 고정 binding point
[`src/program/program.cpp`](../src/program/program.cpp) `BuildUniformBlocks` — `bindingPoint = blockIndex` 를 **블록 의미명 → 전역 고정 슬롯** 으로 교체 (`SemanticBindingPoint`):

| 블록 | 전역 point |
|---|---|
| FrameBlock | 0 |
| DrawBlock | 1 |
| MaterialBlock | 2 |
| LightBlock | 3 |
| (미지 블록) | 4+ 순차 |

```cpp
GLuint SemanticBindingPoint(const std::string& name, GLuint& nextUnknown) {
    if (name == "FrameBlock")    return 0;
    if (name == "DrawBlock")     return 1;
    if (name == "MaterialBlock") return 2;
    if (name == "LightBlock")    return 3;
    return nextUnknown++;
}
// ...
blk.bindingPoint = SemanticBindingPoint(blk.normalizedName, nextUnknownBinding);
glUniformBlockBinding(mProgramAddr, blk.blockIndex, blk.bindingPoint);  // GL 인덱스 -> 의미 슬롯 remap
```
→ 모든 program 의 같은 의미 블록은 같은 전역 point, 다른 의미는 다른 point → **충돌 불가**. 불릿 DrawBlock=1, phong LightBlock=3 분리. (Unity per-semantic constant buffer slot / Unreal uniform buffer slot 정통.)

## 7. 교훈 / 예방
1. **GL 의 active uniform block 열거 순서 != 선언 순서.** "4번째 선언 = index 3" 은 보장 없는 가정. binding point 를 *추론* 하지 말고 의미명으로 *지정* 하거나 실측하라.
2. **program-local 인덱스를 전역 자원 슬롯으로 쓰면 충돌.** `glBindBufferBase` point 는 전역 — 의미별 고정 슬롯이 정통. (`glActiveTexture` 유닛도 동일 계열 함정.)
3. **검증 불가한 가정으로 가설을 기각하지 말라.** 2-3 에서 "LightBlock=3 → 충돌 불가" 로 옳은 가설을 *잘못* 기각했다. 가정이 실측 불가하면 가설 기각이 아니라 **실측 도구를 투입**(변화-게이트 로그).
4. **lit-만-암전 + unlit-정상 = 공유 조명 자원 문제.** 셰이더군별 증상 분리가 원인을 *공유 LightBlock* 으로 빠르게 좁혔다.
5. **이벤트-트리거 + 지속 = 영속 상태 오염.** "프레임마다 복구되면 깜빡임, 지속이면 매 프레임 재오염" — 불릿이 매 프레임 point 1 을 덮는 구조와 일치.
