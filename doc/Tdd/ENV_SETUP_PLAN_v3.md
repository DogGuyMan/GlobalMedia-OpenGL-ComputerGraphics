# 실용적 환경 세팅 계획 v3 — C++ OpenGL 렌더 패스 리팩토링 PoC

> **목표**: Claude Code 5-에이전트 파이프라인이 단일 렌더 패스를 리팩토링하고, 결과를
> **골든 이미지 회귀(pixel diff)** 로 검증하는 최소 실행 가능 환경을 1주 안에 세운다.

**v2 → v3 변경 요약**
- **시드 처리 확정** — 테스트 경로의 **모든 랜덤 시드를 수집·고정 가능**(사용자 확인). v2의 "시드 주입 가능한가?" 미해결 질문이 닫힘.
- **결정성 위험 재정의** — 남은 비결정은 시드가 아니라 **비-시드 잔차**(멀티스레드 FP 순서·async·드라이버)로 좁혀짐. 전 시드 고정 후의 noise floor가 곧 이 잔차의 크기를 분리 측정.
- 그 외 구조(Phase 0~3)는 v2 유지.

**확정된 전제**: 비결정 원천인 랜덤 시드를 **전부 수집·고정 가능**(→ 알고리즘 RNG 결정성 통제됨) · 출력은 텍스처를 렌더 타겟으로 사용(→ read back 가능) · 대상 패스는 **RHI 추상층 뒤(mock 가능)**.

---

## Phase 0 — 가장 먼저 깨질 전제 (PoC 1~2일차, 임계 경로보다 앞)

### 0.1 패스 결정화 (전 시드 수집·고정 + 비-시드 원천 격리)
- **확정**: 테스트 경로에서 쓰이는 **모든 랜덤 시드를 수집(enumerate)해 고정**할 수 있음 → CPU/알고리즘 RNG 비결정성은 통제 가능.
  - 수집 대상: 엔진 RNG, `std::rand`/`mt19937` 등 표준 RNG, 서브시스템별 RNG, **그리고 셰이더 절차적 노이즈를 구동하는 time/frame 유니폼**(이건 1.2의 고정 장면이 핀).
  - 구현 형태: **시드 레지스트리 / 고정 훅** — 골든 실행 직전 모든 시드 소스를 고정 상수로 설정. RHI 추상층 뒤이므로 그 경계로 주입(2.1과 맞물림).
- **남은 위험은 시드가 아니다**: 전 시드를 고정해도 출력이 정착하지 않으면, 원천은 **비-시드 비결정** — 멀티스레드 부동소수점 합산 순서, async/커맨드 큐 순서, GPU 스케줄링, 드라이버 변동. 시드 고정으로는 못 잡는다.
- **판별 절차**: 전 시드 고정 → 동일 머신 N회 렌더 → 픽셀 변동 측정.
  - 변동 0 → 완전 결정적(골든을 비트 단위로 운용 가능). 작은 변동 → 비-시드 GPU/드라이버 잔차 = diff 임계의 하한. 크거나 비정상(non-stationary) → 비-시드 원천이 큼 → 추가 결정화(스레드 수 고정·async 비활성·합산 순서 강제) 필요.
- **요지**: 전 시드 고정은 비-시드 잔차를 깨끗이 분리하는 측정 장치다. **noise floor = 시드로 통제 못 하는 부분의 크기.**

### 0.2 하드웨어·드라이버 고정
- 골든은 GPU·드라이버에 종속된다. **골든 캡처와 검증을 동일 GPU·드라이버에 고정.** PoC 단일 머신이면 자동 충족.
- `ENV_LOCK.md`에 GPU 모델·드라이버 버전·OS·GL 버전 기록. 드라이버가 바뀌면 골든 무효화 가능을 명시.
- (크로스머신·CI는 Phase 3에서 소프트웨어 렌더러 통일 여부로 별도 결정.)

### 0.3 헤드리스 컨텍스트 확인 (캡처는 이미 해결, 컨텍스트만 남음)
- 출력이 텍스처 렌더 타겟에 있으므로 **그 렌더 타겟을 `glReadPixels`/`glGetTexImage`로 직접 read back** → 캡처 해결.
- **[결정 필요]** 남은 건 윈도우 없이 GL **컨텍스트**를 만들 수 있는가뿐. 후보: surfaceless EGL / pbuffer / OSMesa / 숨김 윈도우. 엔진 초기화 방식에 종속 → day-0 소규모 확인.

## Phase 1 — 임계 경로 (1주차 필수)

### 1.1 결정적 빌드
- out-of-source `build/poc/`, 툴체인 고정(→ `ENV_LOCK.md`).
- **주의**: 빌드 결정성 ≠ 렌더 결정성. 렌더 출력 안정성은 Phase 0이 책임진다.
- **[결정 필요]** 대상 패스를 독립 CMake 타겟으로 분리 가능한가, 전체 빌드 후 패스만 실행인가?

### 1.2 골든 이미지 하니스 (회귀 오라클)
- **개념**: 리팩토링은 *동작 보존*이 목적 → 올바른 골든은 리팩토링 **전·후 모두 PASS**. 나쁜 리팩토링이면 **pass→fail** 로 검출. (TDD-Bench의 `fail→pass`는 *동작을 바꾸는* 이슈 수정용이라 여기 직접 대응 안 됨.)
- 결정적 장면 1개 고정(카메라·씬·**전 시드 고정(시드 레지스트리)**·time/frame 유니폼 핀·해상도) → 패스 렌더 → 렌더 타겟 텍스처 read back → PNG.
- 골든 캡처: 리팩토링 *전* PNG = "golden". `/golden-capture` 연결.
- pixel diff: 새 출력 vs 골든, **Phase 0의 noise floor 위로 임계 설정**(추측 금지). noise floor가 0이면 비트 일치 게이트도 가능.

### 1.3 골든 업데이트 게이트 (비협상)
- 골든을 *언제·어떻게* 정당하게 갱신하는지 규정. **`/golden-update`에 사람 승인 게이트 필수.**
- 에이전트가 현재 출력으로 골든을 덮어써 통과시키는 것은 CITYWALK §5.4의 컴파일러-출력 오라클 문제와 동형 → 자동 갱신 금지.

### 1.4 읽기 전용 격리 (점검)
- `hooks.json` 쓰기 범위가 리팩토링 대상으로 제한되는지 확인.
- 골든 PNG·`ENV_LOCK.md`는 읽기 전용 경로에 두어 에이전트가 못 고치게.

### 1.5 verify 스크립트 + 최소 루프
- 단일 `verify` 스크립트: **빌드 → (전 시드 고정) 헤드리스 렌더 → diff → exit 0/1**. Test & Debug가 pass/fail을 기계적으로 읽는 경로.
- 1회 사이클: `골든 캡처 → Refactorer → 재빌드 → 재렌더 → diff → 통과/실패(실패 시 Test & Debug 재실행)`. **수동 1회 완주 = 1주차 성공 기준.**

### 1.6 오라클 사각지대 명시
- 골든은 **필요조건일 뿐**. 이미지가 같아도 (a) 다음 패스로 새는 GL 상태/리소스 바인딩 부작용, (b) 성능·메모리 회귀, (c) 비가시 동작 파손은 못 잡는다.
- 최소한 **렌더 후 GL state 누수·다음 패스 영향**은 별도 점검 항목으로 둘 것.

## Phase 2 — PoC 내 권장

### 2.1 Mock RHI (실현 가능 — RHI 추상층 뒤)
- gmock으로 RHI를 mock → **2단계 검증**: ① RHI mock으로 패스 로직 격리 테스트(결정 입력·**시드 레지스트리로 시드 주입**, 호출 시퀀스 캡처), ② 실제 RHI→실제 GL 헤드리스로 골든 이미지.
- 0.1의 시드 고정 훅을 RHI 경계에 두면 격리 테스트와 골든 실행이 동일한 시드 통제를 공유.

### 2.2 장면 커버리지 확인
- 단일 장면이 리팩토링되는 코드 경로(머티리얼 분기·라이팅 조건·피처 플래그)를 **실제 실행하는지** 확인. (TDD-Bench adequacy 문제)
- 1개로 시작하되, 대상 코드 주요 분기를 깨우는 입력을 의도적으로 포함하거나 커버리지로 검증.

### 2.3 골든 적합성 sanity check (여기가 `fail→pass`가 실제로 쓰이는 곳)
- 렌더 코드에 작은 버그 주입(색상·좌표 오프셋) → 골든 diff가 **FAIL(=kill)** 해야 정상. 살아남으면 장면/임계가 부적합.
- 골든의 **민감도(adequacy / Mutation Score)** 검증. PoC에선 손으로 1~2개.

## Phase 3 — PoC 이후 확장 (지금 만들지 말 것)

- **자동 변이 도구**: 근거 MuTAP(MutPy·kill/survive·살아남은 변이로 보강), TDAD(MutationSmith·MS·비활성 변이 제외). C++ 후보 mull / Dextool mutate — **[검증 필요]** 설치·버전은 현재 문서로 확인(확정 명령 미기재). 그래픽 적용: 변이=렌더 버그 주입, kill=diff 검출.
- **확률성 게이트(RPR)**: 에이전트는 확률적 → N회 재실행 통과율로 판정(표준 N=10·τ≥0.9, 고위험 N=50). 리팩토링 결과 N회 생성→diff 전부 통과해야 머지. (best-of-N 원칙과 일치)
  - *주의*: 렌더 자체는 전 시드 고정으로 결정적이므로, 여기서의 확률성은 **에이전트(LLM) 출력**의 확률성이지 렌더의 확률성이 아님. 둘을 혼동하지 말 것.
- **MCP / CI·CD**: MCP로 build·render·diff 도구 노출. CI는 루프 자동화·골든 LFS 관리. **[결정 필요]** 헤드리스 GL 러너 + **크로스머신 골든** 처리(동일 GPU 고정 vs 소프트웨어 렌더러 llvmpipe/SwiftShader 통일 — 후자는 실제 GPU 경로 미검증).
- **코드 컨벤션(Quality Gate용)**: 사내 규칙 → `clang-format`/`clang-tidy`로 기계화.

## 최우선 리스크 (남은 day-0 검증)
1. **비-시드 비결정 잔차** — 시드는 이제 전부 고정 가능하므로, 출력이 안 정착하면 원인은 GPU/드라이버/스레드 FP 순서다. **전 시드 고정 후 noise floor 측정이 곧 이 잔차의 크기를 직접 보여준다.** 0이면 비트 결정성 확보, 크면 스레드·async 결정화 추가.
2. **헤드리스 컨텍스트 생성** — read back은 해결됐으나 윈도우 없는 GL 컨텍스트 초기화가 안 되면 자동화가 막힌다. day-0 소규모 확인.
